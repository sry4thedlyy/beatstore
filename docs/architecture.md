# Beatstore — архитектурные решения

## Выбранная основа

- React и Next.js App Router — интерфейс и серверная часть одного приложения.
- TypeScript — для интерфейса, серверного кода и описания данных.
- Node.js — серверная среда выполнения.
- PostgreSQL — пользователи, товары, заказы, условия и резервы.
- Yandex Object Storage в российской локации, стандартный класс — обложки, аудио, архивы и демонстрационные документы.
- Better Auth — регистрация по email и паролю, сессии и восстановление доступа. Официальный Drizzle-адаптер подключает библиотеку к PostgreSQL и локальной PGlite.
- ЮKassa — подготовлен адаптер API v3 тестового магазина; без аккаунта используется локальный симулятор. Сервис отправки email предстоит выбрать.

Конкретные версии зависимостей фиксируются при подготовке проекта после проверки совместимости.

### Основа первой итерации

Приложение использует Next.js 16.4.0, React 19.3.0 и TypeScript 6.0.3. Версии фиксируются в `package.json` и `package-lock.json`; локальная среда — Node.js 22.20 или новее совместимой версии.

Доступ к базе выполняется параметризованными SQL-запросами. Миграции хранятся отдельными SQL-файлами с контрольными суммами. Для обычного PostgreSQL используется `pg`, для локального запуска без Docker — PGlite 0.5.8 с сохранением на диск. Оба режима используют одинаковую схему. PGlite допускает один процесс, поэтому миграции и наполнение базы запускаются при остановленном приложении. Обычный PostgreSQL и конкурентные операции между соединениями проверяются перед публичным развёртыванием.

Реализованы публичный каталог, поиск, страницы товаров, лицензии, общий MP3-плеер, авторизация, кабинеты и управление товарами с загрузкой файлов. Оформление фиксирует снимок покупки, тестовая оплата подтверждается сервером, кабинет показывает заказы и сохранённые условия. Выдача файлов и генерация документов остаются отдельным этапом. Подключение и сквозная проверка тестового магазина ЮKassa требуют его ключей.

Демонстрационные обложки и синтезированные аудиопримеры генерируются локально. Временный файловый адаптер выдаёт только обложки и превью опубликованных товаров; платные WAV и ZIP не имеют публичного маршрута. Тестовые архивы STEMS и проекта являются заглушками и требуют замены настоящими материалами перед выдачей покупок. Бакет Yandex Object Storage пока не подключён.

## Структура приложения

Один проект и один выпуск приложения. Внутри — отдельные модули каталога, аккаунтов, заказов, лицензий, файлов и администрирования.

Структура сущностей, связей и ограничений описана в [модели данных](data-model.md).

Бизнес-правила отделяются от компонентов React. Сервер рассчитывает цены, проверяет полномочия, создаёт заказы и выдаёт доступ к файлам. Данные, присланные браузером, проверяются при выполнении операции; TypeScript не заменяет проверку входных данных.

### Аккаунты и доступ

Better Auth 1.7.7 хранит хеши паролей в `auth_accounts`; пользователь и связанные с ним заказы сохраняют прежний UUID. Drizzle ORM 0.45.4 используется для таблиц авторизации, бизнес-запросы продолжают использовать параметризованный SQL. Миграция `002_authentication.sql` добавляет служебные таблицы без изменения первой миграции.

Пароль содержит 12–128 символов. Email нормализуется, имя артиста содержит 1–80 символов. Регистрация создаёт роль `CUSTOMER`; параметры роли из HTTP-запроса отбрасываются, создание пользователя также закрепляет эту роль. Администратор назначается локальной командой существующему аккаунту при остановленной PGlite.

Сессия хранится в базе и действует семь дней. Подписанная cookie имеет `HttpOnly` и `SameSite=Lax`, при HTTPS — `Secure`. Кабинет проверяет сессию на сервере; роль берётся из базы без cookie-кеша. Выход отзывает текущую сессию; смена пароля по ссылке отзывает все сессии пользователя. После входа допускаются только внутренние адреса каталога, кабинета и карточек товаров.

HTTP-маршрут авторизации ограничен регистрацией, входом, выходом, чтением сессии и восстановлением пароля. POST требует совпадения `Origin` с адресом магазина и принимает JSON до 8 КБ. Счётчики попыток хранятся в базе, включая локальный режим: вход — восемь попыток в минуту, регистрация — пять за пять минут, запрос восстановления — три за пять минут. Для локального MVP используется общий лимит для каждого маршрута, без доверия присланным заголовкам IP. Перед публичным размещением необходима конфигурация доверенного обратного прокси и лимитов для реальных клиентов.

Одноразовая ссылка восстановления действует 30 минут; идентификатор токена хранится в виде хеша. Ответ на запрос одинаков для существующего и неизвестного email. В локальном MVP письма сохраняются в `.data/mail` и читаются командой `npm run mail:inbox`; HTTP-доступа к папке нет. Секрет авторизации создаётся командой `npm run auth:setup` в игнорируемом `.env.local`. Файловая почта допускает только loopback-адрес приложения; публичная версия требует настоящего почтового адаптера.

Кабинет покупателя показывает данные аккаунта и количество покупок и ожидающих оплаты заказов, с пустыми состояниями. Кабинет администратора содержит сводку, список всех карточек и создание товара. Редактирование открывается из полной карточки; черновики и снятые товары доступны только администратору. Выдача покупок относится к следующей итерации.

### Управление каталогом

Текстовые поля передаются JSON-запросом до 48 КБ; файл загружается отдельным потоковым PUT-запросом с прогрессом и отменой. Сервер проверяет сессию, роль из базы и `Origin`. Тип товара задаётся при создании; обычные лицензии получают базовые цены 1 000/2 000/3 000 ₽. Редактируются скидка, цена эксклюзива и драмкита.

Миграция `003_catalog_editing.sql` вводит `revision`: изменение блокирует строку товара и требует текущую версию, старая вкладка получает конфликт. При незавершённой оплате, резерве или проданном эксклюзиве изменения запрещены. Проданный эксклюзив нельзя вернуть в публикацию также на уровне базы. Удаление без покупок требует точного названия; снимки отменённых заказов и бесплатных принятий сохраняются с очищенной ссылкой на товар.

Sharp 0.35.5 преобразует обложку в JPEG 1200×1200 и 480×480, удаляя исходные метаданные. Поддерживаются статичные JPEG/PNG/WebP до 10 МБ и 40 мегапикселей. Music Metadata 12.1.0 определяет формат и длительность: MP3 до 50 МБ, WAV до 250 МБ, аудио до часа. Полный MP3 бита служит превью и файлом предложения MP3.

Yauzl 3.4.0 проверяет каталог и локальные заголовки ZIP до 500 МБ, без распаковки: до 10 000 записей и заявленных 2 ГБ после распаковки, без пароля, символических ссылок и повторяющихся имён. STEMS требует WAV, проект — FLP, драмкит — текстовый файл правил. Наличие расширения не подтверждает содержимое FLP или качество звуков; соответствие правил внутри ZIP карточке проверяет администратор.

Байты находятся в `.data/uploads`, вне публичной папки. `PENDING` резервирует место в лимите 1 ГБ; проверка и прикрепление создают новую версию. Неуспешная загрузка убирает свои временные файлы. Прежние готовые версии, включая версии удалённых карточек, сохраняются и учитываются в объёме. Аварийное завершение процесса может оставить служебный исходник или `PENDING`; автоматическая уборка после аварии пока отсутствует.

`/media/<id>` выдаёт опубликованные обложки и MP3. `/api/admin/media/<id>` после проверки администратора позволяет просмотреть обложку и превью черновика; WAV, ZIP и документы через него не выдаются. Потоковые ответы поддерживают диапазоны байтов, не читая всё аудио в память. Публичное размещение потребует S3 с прямой загрузкой крупных файлов, настройки прокси и проверки на отдельном PostgreSQL.

PostgreSQL использует транзакции, ограничения и блокировки для согласованности заказов и продажи эксклюзива. Один успешный платёж должен обрабатываться один раз. Внешний платёж не является частью транзакции базы: задержки и повторы обрабатываются явно.

## Хранение файлов

- Обложки доступны посетителям; при загрузке проверяются формат и размер, изображение обрезается до квадрата, для каталога создаётся уменьшенная версия.
- Аудио и архивы не хранятся в исходном коде или открытой папке приложения.
- Превью доступны для прослушивания посетителям; технически возможно их сохранение пользователем.
- Биты и драмкиты используют общий аудиоплеер. Превью драмкита — один загружаемый MP3-файл; отдельная система обработки видео или демонстрации отдельных звуков не требуется.
- Платные файлы закрыты. Сервер проверяет покупку и выдаёт временную ссылку.
- Временная ссылка может быть передана другому человеку до истечения срока; она не обеспечивает защиту от копирования.
- Файлы оплаченных заказов сохраняются независимо от последующего редактирования или снятия товара с публикации.
- Механизм загрузки крупных архивов уточняется при выборе хранилища, чтобы избежать передачи всего архива через сервер приложения.

### Провайдер и бюджет MVP

Для демонстрационного MVP выбран Yandex Object Storage в российской локации со стандартным классом хранения. До подключения проверяются загрузка архивов, аудиоплеер и временные ссылки. Selectel S3 остаётся альтернативой при изменении условий или требований.

По правилам тарификации, проверенным 10.10.2026, ежемесячно не тарифицируются первый 1 ГБ стандартного хранения, 10 000 операций PUT/POST/PATCH/LIST, 100 000 операций GET/HEAD/OPTIONS и первые 100 ГБ исходящего трафика. Источник: https://yandex.cloud/ru/docs/storage/pricing. У провайдера 1 ГБ = 2^30 байт.

Целевой объём всех демонстрационных файлов — до 1 ГБ. При соблюдении лимитов хранения, операций и трафика расходы на Object Storage могут быть нулевыми. Это не означает бесплатность сервера, базы данных, домена или email. Превышение лимитов тарифицируется; бюджетные уведомления не заменяют ограничения расхода.

В бюджет включаются хранение, исходящий трафик, операции, резервные копии и сохраняемые версии объектов. Доступность данных в основном хранилище не заменяет резервное копирование.

## Демонстрация платежей и документов

По умолчанию используется локальный симулятор `DEMO` с отдельным состоянием провайдера. Подготовлен адаптер `YOOKASSA` для тестового магазина. Сервер фиксирует заказ и попытку до внешнего запроса, сохраняет ключ идемпотентности при сбое сети и сверяет платежи через API. Уведомление и возврат браузера не являются подтверждением. Ошибочная сумма, валюта, окружение или идентификаторы блокируют автоматическую выдачу.

Резерв эксклюзива устанавливается вместе с заказом и блокирует новые покупки всех вариантов. Незавершённые обычные заказы препятствуют открытию оплаты эксклюзива. Подтверждение блокирует товар, заказ и попытку; успех одновременно фиксирует оплату и `EXCLUSIVE_SOLD`. Локальная оплата действует 15 минут, внешний резерв не снимается по локальному времени. Короткая аренда проверки платежа исключает параллельные сетевые операции, не подменяя резерв товара. Сценарии, настройка и ограничения: [Тестовая оплата](payments.md).

Конкурентная продажа эксклюзива, обычная покупка одновременно с эксклюзивом и повторы оформления проверяются на независимом PostgreSQL 18.4 через `npm run test:postgres`. Временная база не связана с рабочей PGlite. Проверки запускаются также в GitHub Actions.

Документы формируются из шаблонов с демонстрационной пометкой и тестовыми данными сторон. Приобретённые условия и список авторов сохраняются независимо от дальнейших изменений товара. Реальная отчётность и выплаты роялти не реализуются.

## Развёртывание — предложение

Разработка и первая демонстрация приложения и PostgreSQL выполняются локально, файловое хранилище отдельно. Публичное размещение и бюджет сервера определяются позднее. Вариант для публичной версии — приложение и PostgreSQL на одном сервере с обслуживанием и резервными копиями.

Резервные копии базы и файлов должны восстанавливаться; наличие копии само по себе не доказывает возможность восстановления.

## Проверки

Проверка типов, серверная валидация, тесты бизнес-правил и основных сценариев покупки. Приоритет: доступ к чужим данным, повторы платежей, конкурентная продажа эксклюзива, скидки и неизменность приобретённых условий.
