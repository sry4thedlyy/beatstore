# Приемка демонстрационного MVP

## Граница готовности

Локальный магазин демонстрирует полный цикл: создание товара, публикацию, регистрацию, оформление одного товара, тестовую оплату, выдачу файлов и PDF, историю покупок. Платежи не списывают деньги, документы не передают реальные права. Рабочий каталог не нужен для приемочных проверок.

Yandex Object Storage и тестовый магазин ЮKassa подключаются отдельно. Отсутствие их аккаунтов и ключей не блокирует локальную приемку. Проверка адаптеров на имитаторах не подтверждает работу настоящих внешних сервисов.

## Воспроизводимая проверка

При остановленном режиме разработки собрать текущий код, затем выполнить:

```sh
npm run build
npm run test:smoke
```

Сценарий запускает **готовую production-сборку** Next.js на свободном loopback-порту. Он создаёт новую папку `work/acceptance-*`, собственные PGlite-базу, файлы, почту, секрет авторизации и тестовые аккаунты. Подготовка базы завершается до запуска сервера. Рабочие `.data/postgres`, файлы и аккаунты не изменяются; внешние платежи и облако принудительно выключены. Успех отмечается сообщением `Acceptance check passed`; ошибка даёт ненулевой код завершения. Проверка включена в GitHub Actions после сборки.

После обычного завершения тестовый сервер останавливается и созданная папка удаляется. Принудительное завершение процесса может оставить тестовую папку в `work`; это не рабочие данные. Не запускать проверки параллельно со сборкой или изменением кода: проверяется последний результат `npm run build`.

Для самостоятельного прохождения интерфейса:

```sh
npm run demo:acceptance
```

Открыть `http://localhost:3100`. Покупатель: `demo@example.test` / `Beatstore-demo-2026`; администратор: `admin@example.test` / `Beatstore-admin-2026`. Каждый запуск создаёт чистую среду, поэтому здесь можно проверять продажу эксклюзива и удаление черновика. Используется отдельное имя хоста `localhost`, чтобы не заменять cookies рабочего магазина на `127.0.0.1`. Остановить сервер через Ctrl+C. Если порт занят, выбрать другой: `npm run test:smoke -- --serve --port=3101`.

Сквозной HTTP-сценарий проверяет настоящие маршруты запущенного приложения, включая серверную выдачу страниц и обработку файлов. Он дополняет тесты бизнес-правил и конкурентных операций PostgreSQL; выполнение браузерного JavaScript, внешний почтовый сервис, реальные ключи и поведение инфраструктуры этими проверками не покрываются.

## Ручной чек-лист перед демонстрацией

1. Открыть каталог на настольном и узком мобильном экранах. Проверить читаемость, поиск, карточки, отсутствие горизонтального прокручивания.
2. Запустить MP3, перемотать, перейти к товару и остановить общий плеер. Проверить превью драмкита.
3. Выбрать WAV, начать покупку гостем, войти. Проверить возвращение к WAV, цену и условия.
4. Сымитировать оплату. Скачать файл и PDF, открыть покупку из кабинета. Сымитировать отказ в отдельном заказе.
5. Принять бесплатные условия и скачать MP3. Вернуться на страницу: та же версия не требует повторного принятия.
6. Администратором создать черновик, сохранить поля, загрузить собственные демонстрационные файлы, опубликовать, проверить карточку и снять с публикации. Незавершённые поля не должны теряться при загрузке.
7. Продать эксклюзив в изолированной среде. Проверить исчезновение бита из каталога и доступность ранее оплаченного WAV из кабинета.

## До публичной демонстрации

- Выбрать размещение и постоянное хранение PostgreSQL/файлов, настроить HTTPS и секреты окружения. PGlite предназначена для локального запуска одним процессом.
- Подключить отправку email и адаптировать ограничение локального почтового режима: сейчас сервер принимает только loopback-адрес магазина. Проверить восстановление через настоящий почтовый ящик.
- Подключить приватный бакет, если выбранное размещение не сохраняет локальные файлы. Пройти `storage:check`, перенос и проверку скачиваний. При постоянном локальном диске Object Storage можно подключить позже.
- Настроить резервное копирование базы и файлов и проверить восстановление отдельной среды.
- Проверить ограничения загрузок и запросов у выбранного хостинга и обратного прокси. Автоматическая очистка незавершённых файлов и фоновая сверка платежей пока отсутствуют.
- Для демонстрации настоящего платёжного сервиса подключить тестовые ключи ЮKassa и проверить уведомления, возврат и потерю соединения. Локальный симулятор остаётся достаточным для демонстрации покупки без внешнего сервиса.

Реальные продажи требуют отдельной подготовки платежей, документов и операционных процессов. Эти задачи не являются условием готовности локального демонстрационного MVP.
