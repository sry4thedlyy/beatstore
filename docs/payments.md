# Тестовая оплата

Beatstore поддерживает только демонстрационные покупки. Данные карт не принимаются и не хранятся приложением, реальные списания и передача прав не выполняются.

## Режимы

- `PAYMENT_PROVIDER=demo` — локальный симулятор без внешнего сервиса. Отдельная таблица `demo_provider_payments` хранит результат симулируемого платежа. Кнопка результата изменяет состояние симулятора; магазин читает его на сервере и применяет те же проверки суммы, заказа, валюты и тестового окружения. Доступен только владельцу заказа в локальной среде.
- `PAYMENT_PROVIDER=yookassa` — адаптер API v3 тестового магазина ЮKassa. Реальное тестирование требует Shop ID и тестового секретного ключа. Адаптер проверен с подставными HTTP-ответами; сквозная проверка в ЮKassa без аккаунта не выполнена.

Временная файловая почта и оба режима пока допускают только loopback-адрес магазина. Публичное размещение требует подключения email и отдельной настройки среды.

## Подключение тестового магазина ЮKassa

1. Создать тестовый магазин в [кабинете ЮKassa](https://yookassa.ru/docs/support/merchant/payments/implement/test-store). Договор для создания тестового магазина не требуется.
2. В локальном `.env.local` задать `PAYMENT_PROVIDER=yookassa`, `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` из тестового магазина. Адаптер принимает только ключ с префиксом `test_`; значения не отправляются в браузер и не включаются в Git.
3. Перезапустить приложение и оформить заказ. После создания платежа перейти на страницу ЮKassa; использовать только [тестовые средства оплаты](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).
4. Вернуться на страницу заказа. Сервер запрашивает статус через API; кнопка «Проверить оплату» позволяет повторить сверку. При временной недоступности сервиса заказ сохраняется.
5. HTTP-уведомления можно настроить при появлении доступного извне HTTPS-адреса `/api/payments/yookassa`. Сервис не сможет доставить webhook на `127.0.0.1`. Локально сверка работает через страницу заказа, без уведомлений.

Источник сценария перенаправления и подтверждения: [Быстрый старт API](https://yookassa.ru/developers/payment-acceptance/getting-started/quick-start). API вызывается сервером, авторизация — Basic, платеж создаётся с `capture=true`, суммой RUB с двумя десятичными знаками и сохранённым ключом идемпотентности. Реквизиты покупателя не передаются в metadata: только UUID заказа и попытки.

## Согласованность заказа и платежа

Оформление блокирует пользователя для ограничения незавершённых заказов, затем товар для проверки состояния и резерва. В одной транзакции фиксируются заказ, цена, принятие демонстрационных условий, снимок покупателя и товара, версия условий, файл и попытка `CREATING`. Ключ запроса UUID уникален для пользователя; повтор возвращает исходный заказ. Изменившаяся версия карточки требует заново проверить цену и условия.

Внешний вызов выполняется после транзакции. При сетевом сбое исходная попытка остаётся `CREATING`; повтор использует тот же ключ и сохранённые параметры. ЮKassa гарантирует идемпотентность 24 часа, поэтому после 23 часов неизвестного результата повторное создание блокируется до ручной сверки. Это консервативный запас, не признак отмены платежа. [Формат взаимодействия](https://yookassa.ru/developers/using-api/interaction-format).

Короткая аренда обработки (`lease_token`, `lease_until`, 30 секунд) предотвращает одновременные сетевые проверки одной попытки. Она не является резервом товара. Таймаут HTTP-запроса — 15 секунд. Проверенная обработка блокирует товар, заказ и попытку; повторный успех не меняет дату оплаты и не дублирует покупку. Старый `pending` не возвращает оплаченный заказ в ожидание.

Проверяются идентификаторы платежа, заказа и попытки, сумма, RUB, `test=true` и `paid=true` для успеха. Адаптер дополнительно проверяет Shop ID получателя и HTTPS-адрес страницы оплаты в доменах ЮMoney/ЮKassa. Некорректный результат остаётся на сверке (`needs_review`), без автоматической выдачи или снятия резерва.

Webhook использует только внешний идентификатор как повод для GET-запроса к API. Статус, сумма и прочие поля уведомления не подтверждают оплату. Неизвестные идентификаторы игнорируются; раннее уведомление до сохранения внешнего ID восстанавливается последующей сверкой. [Проверка уведомлений](https://yookassa.ru/developers/using-api/webhooks).

## Резерв и отмена

Локальный симулятор отменяет неоплаченный платёж через 15 минут при следующем обращении. Эксклюзив резервируется в той же транзакции, что и заказ. Пока есть ожидающие обычные покупки, оплату эксклюзива открыть нельзя. Подтверждённый отказ освобождает только резерв своего заказа; подтверждённый успех одновременно отмечает заказ оплаченным и товар `EXCLUSIVE_SOLD`.

Внешний `pending` не отменяется продавцом этим API. При «Отменить заказ» сервер проверяет статус; для `waiting_for_capture` запрашивает отмену, для `pending` сохраняет ожидание до отмены на стороне ЮKassa. Локальный ориентир 24 часа не освобождает товар. Неизвестный результат и неожиданное подтверждение уже отменённого заказа требуют ручной сверки; автоматической повторной продажи или выдачи нет.

Фоновая сверка, инструменты ручного разрешения `needs_review`, возвраты и чеки не реализованы. Покупатель может открыть свой заказ и проверить статус; новая покупка проверяет истёкшие платежи соответствующего товара. Выдача использует зафиксированные `order_files` и снимок условий; `needs_review` блокирует скачивание файлов и документов. Подготовка PDF выполняется после подтверждения оплаты и восстанавливается при открытии заказа. [Файлы и документы](delivery.md).

## Проверки

`npm test` проверяет бизнес-сценарии в отдельных PGlite-базах. `npm run test:postgres` создаёт независимый временный PostgreSQL 18.4 и проверяет две покупки эксклюзива, обычную покупку одновременно с эксклюзивом, повтор одного запроса и повторное подтверждение. Обе команды не меняют рабочую базу. Адаптер ЮKassa проверяется подставным транспортом без сетевых вызовов и секретов.
