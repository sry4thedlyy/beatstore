# Проверка минимального VPS

Кандидат для короткой демонстрации: 1 CPU, 1 ГБ RAM, 10 ГБ диска. Достаточность проверяется сначала в Linux-контейнере GitHub Actions, затем на выбранном VPS. Результат контейнера не гарантирует скорость процессора, диска и сети Beget или достаточность памяти конкретного образа ОС.

## Автоматическая проверка

Задача `capacity` в `.github/workflows/checks.yml` запускает Ubuntu 24.04, Node.js 22.20, production-сборку Next.js, PostgreSQL 16 с настройками по умолчанию и Caddy 2. Все сервисы и тестовый клиент разделяют **одно ядро и 768 МиБ RAM без swap**. Остальные 256 МиБ предполагаются для ОС и SSH; фактический расход ОС проверяется на сервере. База, товары, аккаунты и файлы создаются в отдельной временной папке. Секреты и данные разработки не входят в образ.

Проверяются:

- Полный цикл регистрации, покупки, генерации PDF, приватной выдачи файлов, продажи эксклюзива и восстановления пароля. Почта сохраняется локально; реальные SMTP и платёжный сервис проверяются отдельно.
- Пять посетителей с паузой 250 мс между запросами: каталог, поиск, обложка и MP3-превью. Не менее 100 завершённых запросов, без ошибок; 95% ответов должны завершаться быстрее двух секунд в локальной сети контейнера. Это критерий небольшого показа, а не обещание скорости из интернета.
- Загрузка через Caddy ZIP ровно 500 МиБ, тестовая покупка и полное скачивание с совпадением SHA-256. Архив содержит искусственные данные для проверки передачи и структуры ZIP. Клиент читает и пишет порциями, не удерживая архив целиком в памяти. Загрузка обложки проверяет также создание квадратной версии и миниатюры.
- Отсутствие событий нехватки памяти и принудительного завершения процессов. Пиковая сумма анонимной, разделяемой и памяти ядра по выборкам каждые 100 мс должна оставлять 15% запаса внутри бюджета приложения.

Журнал содержит `CAPACITY_MEMORY` и `CAPACITY_TRAFFIC`. Пик `memory.peak` включает файловый кеш и может приближаться к лимиту при передаче большого архива; кеш может освобождаться ядром. Память процессов оценивается отдельно по `memory.stat`, без многократного подсчёта общих страниц PostgreSQL. Короткие пики между выборками могут не попасть в эту оценку; события OOM и общий пик учитывает само ядро.

Сборка и установка зависимостей выполняются **до ограничения памяти**. Прохождение теста подтверждает только работу готового приложения. Для обновления на маленьком VPS потребуется отдельно проверить сборку со swap либо подготовить совместимую Linux-сборку вне сервера. Windows-сборка не переносится на Linux вместе с Windows-зависимостями.

Для повторения на Linux с Docker, Node.js и уже установленными зависимостями:

```sh
npm run build
docker build -f deploy/capacity.Dockerfile -t beatstore-capacity .
docker run --rm --cpus=1 --memory=768m --memory-swap=768m --shm-size=128m beatstore-capacity
```

Для проверки production-цикла на обычном PostgreSQL без ограничения ресурсов: `npm run test:smoke:postgres`. Это отдельный временный кластер из пакета embedded-postgres; рабочая база не используется. Контейнер использует PostgreSQL 16 из Ubuntu через `PG_BIN_DIR`.

Для проверки с установленным Caddy задать `CADDY_BIN` путём к его исполняемому файлу и выполнить `npm run test:smoke:postgres -- --proxy --large-files`. Этот вариант проверяет прокси и большой ZIP без ограничения памяти, в том числе на Windows. Он не заменяет Linux-тест конфигурации.

## Проверка на выбранном сервере

После успешного предварительного теста подготовить VPS по [инструкции размещения](deployment.md) и пройти [сценарии приёмки](acceptance.md). Во время работы наблюдать `free -m`, `df -h`, `top` и журнал службы. Проверить пять одновременных посетителей, собственную обложку, большой ZIP, скачивание и PDF. Затем перезапустить службу и убедиться, что заказы и файлы сохранились. Проверить HTTPS и восстановление пароля через реальную почту.

Условия принятия: нет ошибок и перезапусков из-за нехватки памяти, интерфейс отвечает без заметных задержек, после загрузок остаётся минимум 2 ГБ свободного диска, копия создаётся и восстанавливается. В эти 2 ГБ должны помещаться временные файлы и резервная копия при демонстрационной квоте 1 ГБ. Тест контейнера не ограничивает диск и не проверяет полный диск образа VPS; 10 ГБ подтверждаются только после установки и измерения на сервере.

Если 1 ГБ не хватает, проверить конфигурацию 2 ГБ. Swap полезен для сборки и редких пиков, но постоянное использование swap при показе означает недостаточный запас RAM. При изменении зависимостей или сценария повторить предварительную проверку.

Источники: [ограничения ресурсов Docker](https://docs.docker.com/engine/containers/resource_constraints/), [счётчики памяти cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html).
