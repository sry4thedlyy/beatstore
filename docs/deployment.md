# Публичная демонстрация

Профиль размещения: один VPS в РФ, Next.js и отдельный PostgreSQL на нём, приватные файлы на постоянном диске, SMTP для восстановления пароля. Оплата работает через демонстрационный симулятор; реальные деньги не принимаются. Подключение Yandex Object Storage можно выполнить отдельно.

## Стоимость и короткие показы

Ориентир Beget для Санкт-Петербурга — 2 CPU, 2 ГБ RAM, 30 ГБ диска: 27 ₽/сутки плюс 5 ₽/сутки за IPv4, суммарно около 1,33 ₽/час. 200 ₽ соответствуют примерно 150 часам существования этих ресурсов. Итоговую конфигурацию, тариф и минимальную сумму пополнения нужно проверить в панели перед созданием сервера. Это оценка расхода, а не подтверждение возможности пополнения ровно на 200 ₽.

Beget тарифицирует время **существования** услуги, с округлением неполного часа вверх. Выключение приложения или ОС не удаляет оплачиваемые ресурсы. Архивные серверы, сохранённые IPv4, образы и снапшоты также оплачиваются. Для редких показов предусмотрен порядок: создать VPS, восстановить приложение, показать, сделать и проверить копию вне VPS, затем удалить сервер и ненужные связанные услуги через панель. Удаление допустимо только после проверки восстановления.

Для постоянной доступности сервер необходимо сохранять между показами и оплачивать это время. Автоматического создания или удаления ресурсов проект не выполняет.

Источники: [конфигурации Beget](https://beget.com/ru/vps), [правила почасовой тарификации](https://beget.com/ru/kb/manual/virtual-servers). Цены могут меняться.

## Сервер и адрес

Начальная конфигурация: Ubuntu 24.04, Node.js 22.20 или новее совместимой версии, PostgreSQL 16, Caddy 2. Приложение слушает только `127.0.0.1:3000`; Caddy принимает HTTPS на 443 и перенаправляет HTTP с 80. PostgreSQL доступен только локально, порт 5432 и порт приложения не открываются в интернет. SSH использует ключ владельца.

Без покупки домена можно зарегистрировать бесплатное имя вида `имя.duckdns.org` в [DuckDNS](https://www.duckdns.org/) и указать IPv4 VPS. Это DNS, сервер остаётся в РФ. Доступность выбранного адреса из сетей посетителей необходимо проверить. Для обычного VPS бесплатное техническое имя Beget в данном профиле не предполагается. Перед освобождением IP удалить его из DNS; после следующего создания VPS обновить запись на новый адрес.

При установке использовать [официальные инструкции Node.js](https://nodejs.org/en/download), пакет PostgreSQL из Ubuntu и [официальный пакет Caddy](https://caddyserver.com/docs/install#debian-ubuntu-raspbian). Node должен быть доступен системной службе через `/usr/bin/env node`, а не только через профиль интерактивного пользователя. Для сборки на 2 ГБ может понадобиться swap; достаточность памяти проверяется на выбранном сервере. Такая конфигурация предназначена для небольшого показа, нагрузочный тест ещё не выполнен.

## Первое развёртывание

Все команды ниже выполняются на подготовленном VPS. До создания ресурса проверить цену в панели. При повторном размещении вместо новой демонстрационной базы использовать [восстановление резервной копии](backups.md).

1. Создать системного пользователя `beatstore`, каталог `/opt/beatstore` с владельцем `beatstore`. Клонировать репозиторий туда и выбрать проверенный коммит. Установить зависимости через `npm ci` от имени `beatstore`.
2. Создать отдельную роль PostgreSQL `beatstore` с правом входа и пустую базу `beatstore`, принадлежащую ей. Задать пароль интерактивно командой `\password beatstore` в `psql` от администратора PostgreSQL. Приложению не нужны права суперпользователя или создания баз.
3. Выполнить `npm run auth:setup` от имени `beatstore`: случайные секреты авторизации и резервной копии сохранятся в `.env.local`, существующие значения останутся прежними. Заменить локальный адрес на реальный HTTPS-адрес и заполнить настройки ниже. Файл должен принадлежать `beatstore`, иметь права `600`; секрет резервной копии сохранить также отдельно от VPS и архивов.
4. При остановленном приложении выполнить `npm run db:setup`. Это миграции, два бита и два драмкита с демонстрационными файлами. Для публичного показа не выполнять `account:demo`: известные тестовые пароли не допускаются.
5. Выполнить `npm run account:owner -- адрес-владельца@example.ru`. Новый администратор получает случайный пароль в приватном файле `.data/owner-access`. Прочитать его самостоятельно на сервере; пароль не выводится в журнал. Уже существующий администратор сохраняет свои данные. Для существующего покупателя роль назначается отдельно через `account:admin`, без изменения пароля.
6. Выполнить `npm run build`, `npm run mail:check` и `npm run deployment:check`. Последняя команда проверяет публичные настройки, миграции, администратора, отсутствие известных демонстрационных паролей, доступность локального хранилища и SMTP. Проверка подключения не отправляет email.

Пример публичных настроек — все заглушки заменяются локально на сервере:

```dotenv
DB_DRIVER=postgres
DATABASE_URL=postgresql://beatstore:URL_ENCODED_PASSWORD@127.0.0.1:5432/beatstore
BETTER_AUTH_URL=https://YOUR_NAME.duckdns.org
BETTER_AUTH_SECRET=GENERATED_SECRET
MAIL_DRIVER=smtp
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_USER=YOUR_MAILBOX@yandex.ru
SMTP_FROM=YOUR_MAILBOX@yandex.ru
SMTP_PASSWORD=YOUR_APP_PASSWORD
STORAGE_DRIVER=local
PAYMENT_PROVIDER=demo
BACKUP_PASSPHRASE=GENERATED_BACKUP_SECRET
```

Пароль PostgreSQL в URL должен быть закодирован для URL. Значения с пробелами или `#` в `.env.local` заключаются в кавычки. Секреты не включаются в Git и не пересылаются в переписке.

## HTTPS и запуск

В `/opt/beatstore/deploy/Caddyfile` заменить `demo.example.test` на выбранное DNS-имя. Проверить, что имя указывает на текущий IPv4. Установить конфигурации от администратора сервера:

```sh
sudo install -m 644 /opt/beatstore/deploy/beatstore.service /etc/systemd/system/beatstore.service
sudo install -m 644 /opt/beatstore/deploy/Caddyfile /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl daemon-reload
sudo systemctl enable --now beatstore
sudo systemctl reload caddy
sudo systemctl status beatstore --no-pager
```

Перед запуском `.data` и `.next` должны существовать и принадлежать `beatstore`. Служба работает без root; запись разрешена только в этих двух каталогах. Caddy получает сертификат автоматически при корректном DNS и доступных портах 80/443. Конфигурация допускает загрузку файла до 500 МБ с запасом на оболочку запроса; ограничения типов и размеров повторно проверяет приложение.

При обновлении: остановить `beatstore`, сделать копию, обновить код и зависимости, выполнить `db:migrate`, собрать, пройти `deployment:check`, запустить. Применённые SQL-миграции не редактируются. База и версии файлов остаются на диске при перезапуске службы или VPS.

## Почта

Для небольшого показа подойдёт отдельный ящик Яндекса и пароль приложения для почтового клиента. Настроить разрешение SMTP согласно [инструкции Яндекса](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others). Отправитель соответствует разрешённому ящику. Поддерживаются порт 465 с TLS и 587 с обязательным STARTTLS; проверка сертификата включена. Основной пароль аккаунта не используется.

`mail:check` проверяет соединение и авторизацию, но не доставку в папку «Входящие». После запуска зарегистрировать собственный тестовый аккаунт и пройти восстановление через реальный email, включая папку спама. Ссылка должна вести на публичный HTTPS-адрес, использоваться один раз и отзывать прежние сессии. Ошибка SMTP записывает только общее сообщение, без адресов, ответов провайдера и токенов; отправка не заменяется сохранением письма на диск.

Письмо отправляется после ответа на запрос. Ответ не раскрывает наличие аккаунта. Очереди с гарантированным повтором отправки нет: после сбоя посетитель может повторить запрос. Локальная разработка сохраняет `MAIL_DRIVER=file` и папку `.data/mail`.

## Проверка перед показом и завершение

Пройти [ручной чек-лист](acceptance.md) по публичному адресу: вход, настоящее восстановление пароля, аудио с перемоткой, тестовая покупка, ZIP/WAV/PDF, доступ из другого аккаунта, загрузка собственного файла. Отдельно перезапустить службу и проверить сохранность заказа и файлов. Синтезированные материалы не являются настоящим комплектом FL Studio.

Во время показа хранение находится на постоянном диске VPS; облачный бакет не обязателен. Копия, оставленная только на этом диске, не защищает от удаления VPS. После показа остановить приложение, создать зашифрованную копию, перенести её и сохранённый коммит на компьютер, проверить восстановление в новой базе и каталогах по [инструкции](backups.md). Только затем удалить сервер, освобождённый IPv4 и ненужные платные снапшоты/образы в панели. Проверить список оставшихся услуг и расход. Не удалять DNS-имя, если оно понадобится снова, но убрать старую IP-запись.

Публичное размещение требует аккаунта провайдера, выбранного адреса и реального SMTP. Готовность к коммерческому запуску, реальные платежи, автоматический мониторинг, независимое регулярное хранение копий и юридическая проверка документов остаются отдельными задачами. Общие лимиты маршрутов авторизации используются для всех посетителей; заголовки IP клиента не принимаются на доверие. Для небольшого показа это допустимое ограничение, для дальнейшего роста потребуется настройка доверенного прокси и лимитов.
